# ТЗ: CRM для стоматологических клиник (SaaS, «как amoCRM»)

Проект строится на форке Atomic CRM (React + react-admin + Supabase). Это **не МИС и не расписание** — это CRM продаж: лиды, воронки, переписка, задачи, отчёты. Запись и приём пациента фиксируются вручную статусом, без календаря и медицинских карт.

## 1. Общие принципы

- **Мультитенантность (SaaS):** одна инсталляция, каждая клиника — отдельная организация (`organization`). Все таблицы содержат `organization_id`, изоляция через Supabase RLS. Пользователь принадлежит одной организации. Atomic CRM из коробки мультитенантность не поддерживает — это первая архитектурная задача.
- **Язык интерфейса:** русский. Даты/телефоны в формате KZ (+7).
- **Платформа:** десктопный браузер. Мобильная адаптация не нужна в MVP.
- **Стиль:** канбан-first, как amoCRM. Карточка сделки открывается справа/по клику, чат внутри карточки.

## 2. Роли

| Роль | Права |
|---|---|
| Владелец клиники | всё, настройки, отчёты, биллинг организации |
| Руководитель | отчёты, настройка воронок/автоматизаций, распределение лидов, все сделки |
| Администратор / куратор | свои и общие сделки, чаты, задачи; не видит настройки и отчёты по другим |
| Врач (опционально, позже) | только просмотр карточки пациента и комментарии |

Администраторы и кураторы — одна техническая роль `manager`, различаются только тем, какие сделки им назначены.

## 3. Сущности

### Пациент (`patient`) — переделать из `contact` Atomic CRM
- ФИО, телефоны (несколько), дата рождения, город
- Мессенджеры: WhatsApp-номер, Instagram-ник, Telegram
- Источник первого обращения
- Теги
- Ответственный сотрудник
- История: все сделки, вся переписка, все задачи, все звонки
- Один пациент — много сделок (обращений)

Сущность `company` из Atomic CRM **удалить** — не нужна.

### Сделка / Обращение (`deal`)
Каждое обращение = отдельная сделка. Поля:
- Пациент (обязательно)
- Воронка и стадия
- Источник (WhatsApp / Instagram / Telegram / звонок / сайт / 2GIS / рекомендация / другое)
- Направление/услуга (справочник, настраивается клиникой: имплантация, ортодонтия, терапия, гигиена…)
- Сумма плана лечения, сумма оплачено
- Ответственный
- Причина отказа (справочник, обязательна при переводе в «Отказ»)
- Дата записи на приём, дата визита (вводятся вручную)
- Метки времени: создано, первый ответ, смена стадий (для аналитики)

### Воронка (`pipeline`) и стадии (`stage`)
- Клиника создаёт любое количество воронок и стадий сама (UI настройки: добавить, переименовать, перетащить порядок, цвет).
- Стадии имеют тип: `open` / `won` / `lost`. Минимум одна `won` и одна `lost` в воронке.
- Предустановленный шаблон при создании организации:
  `Новый лид → В работе → Записан → Пришёл на консультацию → План согласован → В лечении → Лечение завершено (won) → Отказ (lost)`
- Сделку можно переносить между воронками.

### Задача (`task`)
- Текст, срок (дата+время), ответственный, привязка к сделке
- Типы: звонок, написать, напомнить, другое
- Статусы: открыта / выполнена / просрочена (просрочена = вычисляется)

### Сообщение (`message`)
- Привязка к пациенту и к сделке (текущей активной)
- Канал: whatsapp / instagram / telegram
- Направление: входящее / исходящее, автор (сотрудник или система)
- Текст, вложения (фото, файлы), статус доставки
- Внешний id сообщения для дедупликации

### Звонок (`call`)
- В MVP: ручная фиксация (входящий/исходящий, длительность, комментарий). Интеграция с телефонией — позже, структура должна это позволять.

### Заметка (`note`) — из Atomic CRM, оставить.

## 4. Экраны

1. **Канбан воронки** — колонки-стадии, карточки сделок: пациент, услуга, сумма, ответственный, индикатор «нет задачи» (красный), «просрочена задача», непрочитанные сообщения. Переключатель воронок сверху. Drag&drop между стадиями. Фильтры: ответственный, источник, услуга, период, теги.
2. **Карточка сделки** — слева поля сделки и пациента, справа лента: чат + задачи + заметки + история стадий в одном таймлайне. Внизу поле ввода сообщения с выбором канала. Блок «Чек-лист стадии» (см. п. 6).
3. **Список пациентов** — таблица с поиском по ФИО/телефону, дублями не заниматься в MVP кроме поиска по телефону при создании.
4. **Задачи** — мои задачи на сегодня / просроченные / все, по сотрудникам для руководителя.
5. **Инбокс** — все непрочитанные диалоги по всем каналам, как в amo: список чатов слева, переписка справа, кнопка «создать сделку из чата» если у входящего нет открытой сделки.
6. **Отчёты** (руководитель) — см. п. 7.
7. **Настройки организации** — воронки и стадии, справочники (услуги, источники, причины отказа), сотрудники и роли, правила распределения, автоматизации, шаблоны сообщений, подключение WhatsApp/Instagram/Telegram.

## 5. Входящие лиды и распределение

- Новое входящее сообщение с неизвестного номера → автоматически создаётся пациент + сделка на первой стадии выбранной по умолчанию воронки, источник = канал.
- С известного номера и открытой сделкой → сообщение прикрепляется к ней.
- С известного номера без открытой сделки → создаётся новая сделка (повторное обращение).
- Формы с сайта / 2GIS: webhook-эндпоинт `POST /api/leads` с токеном организации, поля: имя, телефон, источник, услуга, комментарий.
- **Распределение — настраивается** в настройках организации, режимы:
  - по очереди (round-robin) среди выбранных сотрудников;
  - вручную (лид висит на «Нераспределённые», руководитель назначает);
  - «кто первый ответил — тот и ведёт».
  - Опционально: правило по источнику/услуге → конкретный сотрудник.

## 6. Автоматизации (MVP)

Движок правил «событие → действие», редактируется в настройках:

- **Автозадачи при смене стадии:** для каждой стадии можно задать: создать задачу типа X с текстом Y через N часов/дней ответственному.
- **Контроль «сделка без задачи»:** у любой открытой сделки должна быть открытая задача. Если нет — карточка подсвечивается на канбане и попадает в отчёт руководителя. Просроченные — отдельно.
- **Напоминания пациенту в WhatsApp:** для стадии можно задать автосообщение по шаблону через N часов/дней (например, «Записан» → за день до визита напоминание; «Отказ» → через 30 дней реактивация). Шаблоны с переменными `{имя}`, `{услуга}`, `{дата_визита}`, `{клиника}`. Обязательный переключатель «отправлять автоматически / сначала показать сотруднику».
- **Чек-листы/скрипты для админа:** для каждой стадии клиника задаёт текст скрипта и список пунктов чек-листа; они показываются в карточке сделки, пункты отмечаются, отметки сохраняются по сделке.

## 7. Отчёты (руководитель)

Все с фильтром по периоду, воронке, сотруднику, источнику:

1. **Конверсия** — воронка по стадиям (сколько дошло до каждой), в разрезе источников и сотрудников. Ключевые: лид→запись, запись→визит, визит→план согласован, план→оплата.
2. **Скорость и KPI** — среднее время первого ответа на входящее сообщение, среднее время в стадии, количество сделок/задач/сообщений по сотруднику, доля просроченных задач.
3. **Причины отказа** — распределение по справочнику, по стадии, на которой ушли.
4. **Деньги** — сумма планов лечения (согласованных), сумма оплачено, средний чек, по услугам и сотрудникам. Данные вводятся вручную в сделке.

Экспорт любого отчёта в CSV.

## 8. Интеграции

- **WhatsApp — неофициальный, через QR** (библиотека Baileys или whatsapp-web.js, отдельный Node-сервис). Каждая организация подключает свой номер сканированием QR в настройках. Сервис держит сессии по организациям, пишет входящие в Supabase, отправляет исходящие через очередь. Обязательно: статус сессии в UI («подключено / требуется QR»), переподключение, лимит на массовые рассылки (антибан: задержки, не более N сообщений в минуту).
- **Instagram Direct / Telegram** — структура каналов универсальная (`channel_connection` на организацию с типом и credentials); в MVP реализовать WhatsApp, остальные — адаптеры позже. Telegram проще всего через Bot API, сделать вторым.
- **Формы / 2GIS** — webhook из п. 5.
- **Телефония** — не в MVP, но модель `call` готова.

## 9. Технические требования

- Стек: как у Atomic CRM (React, react-admin, TypeScript, Supabase: Postgres + Auth + Storage + Edge Functions). Отдельный сервис для WhatsApp на Node.
- RLS на всех таблицах по `organization_id`; проверять, что сотрудник одной клиники никак не видит данные другой.
- Все справочники и настройки — в таблицах, не в коде.
- Миграции Supabase в репозитории, сиды с демо-организацией и шаблонной воронкой.
- Real-time обновление канбана и чата (Supabase Realtime).
- Логи действий по сделке (кто, когда, что изменил).

## 10. Порядок реализации

1. Мультитенантность: организации, приглашение сотрудников, роли, RLS.
2. Переделка сущностей: `contact`→`patient`, удалить `company`, расширить `deal`, настраиваемые воронки/стадии, справочники.
3. Канбан + карточка сделки + задачи + контроль «без задачи».
4. WhatsApp-сервис (QR, входящие → автосоздание сделок, исходящие из карточки), инбокс.
5. Распределение лидов, автозадачи, чек-листы стадий.
6. Автосообщения по шаблонам.
7. Отчёты.
8. Webhook для форм, Telegram-адаптер.

Каждый этап — рабочий и демонстрируемый; после каждого этапа — тесты RLS и короткий README по тому, что появилось.

## 11. Не делаем (чтобы не расползлось)

Расписание врачей, медкарты, зубная формула, склад, кассы/чеки, интеграция с МИС, мобильное приложение, email-рассылки.
