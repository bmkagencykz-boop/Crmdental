# Этап 1. Мультитенантность, роли, RLS

## Что появилось

**Клиники (организации).** Любой посетитель регистрирует клинику со страницы входа («Зарегистрировать клинику»). Создаётся организация, а зарегистрировавшийся становится её владельцем. Один пользователь принадлежит одной клинике.

**Роли** (`sales.role`):

| Роль | Что может |
|---|---|
| `owner` — владелец | всё: сотрудники, настройки, название клиники; биллинг — в следующих этапах |
| `head` — руководитель | настройки, все данные, видит список сотрудников |
| `manager` — администратор / куратор | работа со сделками, пациентами, задачами; настройки не видит |

**Сотрудники.** Владелец приглашает их по email в разделе «Сотрудники» и выбирает роль: руководитель или администратор. Отключённый сотрудник теряет доступ к данным. Роль и статус самого владельца менять нельзя.

**Изоляция данных.** Во всех таблицах есть `organization_id`: он проставляется автоматически, а RLS-политики пускают только в свою клинику. Ссылки между таблицами проверяются составными внешними ключами `(organization_id, id)`, поэтому нельзя, например, повесить задачу на пациента чужой клиники. Файлы лежат в хранилище в папке `<organization_id>/`, и доступ к ним тоже ограничен своей клиникой.

**Интерфейс на русском** (английский оставлен запасным языком). Валюта по умолчанию — тенге. Стадии сделок и услуги по умолчанию стоматологические; в этапе 2 они переедут в настраиваемые таблицы.

## Как устроено

- Схема: `supabase/schemas/`, миграция `supabase/migrations/20260927000000_init_multitenant.sql`. Миграции Atomic CRM схлопнуты в одну базовую: продакшн-данных ещё не было.
- `private.current_organization_id()` и `private.current_user_role()` — функции-помощники для RLS и значений по умолчанию.
- `handle_new_user` (триггер на `auth.users`) работает так:
  - при самостоятельной регистрации создаёт клинику и владельца;
  - при приглашении берёт клинику и роль из `app_metadata`, которую может записать только сервисная роль (edge function `users`). Роль владельца через приглашение выдать нельзя.
- Edge functions:
  - `users` работает только внутри клиники вызывающего, сотрудниками управляет только владелец;
  - `delete_note_attachments` удаляет файлы только из папки своей клиники;
  - `postmark` (приём email) и `mcp` удалены: они не нужны по ТЗ и обходили изоляцию.
- Настройки интерфейса (`configuration`) хранятся отдельно для каждой клиники. Менять их могут владелец и руководитель.

## Тесты

`make test-db` (см. README):
- [`001_tenant_isolation.test.sql`](../../supabase/tests/001_tenant_isolation.test.sql):
  - сотрудник клиники B не видит ни одной таблицы и ни одного представления клиники A;
  - не может ничего изменить, удалить или вставить в клинику A;
  - не может сослаться на её записи и не может перенести свои записи в неё;
  - анонимный и отключённый пользователи не видят ничего.
- [`002_roles_and_invites.test.sql`](../../supabase/tests/002_roles_and_invites.test.sql):
  - приглашения, запрет второго владельца, запрет выбрать клинику через `user_metadata`;
  - права ролей на настройки и организацию, запрет менять тариф;
  - изоляция файлов.

Проверено мутационно: если открыть политику чтения, тест падает.

Unit-тесты: `canAccess.test.ts` (права ролей в интерфейсе), `i18nProvider.test.ts` (русский язык и множественные формы), `isInOrganizationFolder.test.ts` (проверка папки клиники при удалении файлов).

## Известные ограничения

- Бакет `attachments` публичный, как в Atomic CRM: файл открывается по прямой ссылке без авторизации (имена случайные). Перед этапом с перепиской стоит перевести его на подписанные ссылки: там будут фото пациентов.
- e2e-тесты Playwright обновлены под регистрацию клиники, но в среде разработки их не запускали: нет Docker для локального Supabase. Их прогонит CI.
- Биллинг (тарифы и оплаты) пока только поля в `organizations` (`plan`, `trial_ends_at`). Менять их может только сервисная роль.
