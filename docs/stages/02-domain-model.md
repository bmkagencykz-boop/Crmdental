# Этап 2. Пациенты, сделки, воронки, справочники

## Что появилось

**Пациенты вместо контактов, компаний больше нет.** Карточка пациента: ФИО, несколько телефонов, дата рождения, город, WhatsApp, Instagram, Telegram, источник первого обращения, теги, ответственный. На странице пациента — все его обращения (сделки), звонки и заметки. Телефоны приводятся к виду `+7XXXXXXXXXX`, поэтому пациента находят по любому написанию номера: `8 701 123 45 67`, `+7 (701) 123-45-67`. При вводе номера, который уже есть в базе, появляется подсказка со ссылкой на найденного пациента. При создании сделки пациента с таким номером предлагают выбрать, а не создавать заново.

**Сделка = обращение.** У сделки есть пациент (обязательно), воронка и этап, источник, услуга, сумма плана лечения, оплачено, ответственный, причина отказа с комментарием, дата записи и дата визита. Время создания, смены этапа и закрытия база проставляет сама. Время первого ответа появится вместе с перепиской (этап 4).
- **Оплаты** — отдельная таблица. «Оплачено» считается как их сумма, вручную это поле не меняется.
- **История** — каждое создание, смена этапа и изменение полей пишется в журнал сделки. Журнал видно в карточке.
- У одного пациента может быть сколько угодно сделок.

**Воронки и этапы настраивает клиника** (Настройки → Воронки): добавить, переименовать, поменять порядок и цвет, задать тип (в работе / успех / отказ). Новая клиника получает шаблон из ТЗ: «Новый лид → В работе → Записан → Пришёл на консультацию → План согласован → В лечении → Лечение завершено → Отказ».

База проверяет правила сама:
- в воронке всегда есть хотя бы один успешный этап и один этап отказа;
- этап со сделками удалить нельзя;
- сделку можно перенести в другую воронку. По умолчанию она попадает на первый этап новой воронки. Клиника может разрешить выбирать этап (Настройки → Права доступа).

**Отказ.** Перевести сделку в отказ без причины нельзя: при перетаскивании на канбане открывается окно выбора причины, в форме появляется обязательное поле. Сделка в отказе обратно в работу не возвращается. Для повторного обращения создаётся новая сделка.

**Справочники** (Настройки): услуги, источники, причины отказа. Ненужное значение можно скрыть, не удаляя. Системные источники (WhatsApp, Instagram, Telegram, звонок, сайт, 2GIS, рекомендация, другое) удалить нельзя: по ним будут работать интеграции.

**Что видит администратор** (Настройки → Права доступа): все сделки клиники, только свои или свои и без ответственного. Владелец и руководитель видят всё. Правило действует на уровне базы (RLS): вместе со сделкой скрываются её задачи, заметки, оплаты и история.

**Канбан и задачи** (частично — задел этапа 3):
- переключатель воронок сверху;
- фильтры по ответственному, источнику, услуге и поиск по имени или телефону;
- у колонки — число сделок и сумма, быстрое добавление сделки;
- карточка сделки показывает пациента, услугу, сумму, ответственного и метки «Нет задачи» / «Просрочено».

У задачи есть тип (звонок, написать, напомнить, другое), и она привязана к сделке. Звонки фиксируются вручную: направление, длительность, комментарий.

**Демо** (`make start-demo`, данные в браузере) повторяет те же правила, что и база.

## Как устроено

- Схема: `supabase/schemas/`, миграция `20260928000000_stage2_domain_model.sql`. Таблицы: `patients`, `deals`, `pipelines`, `stages`, `services`, `lead_sources`, `lost_reasons`, `deal_payments`, `deal_events`, `calls`, `organization_settings`. Представления: `patients_summary`, `deals_summary` (пациент, тип этапа, открытые задачи и ближайший срок — для меток «Нет задачи» / «Просрочено»).
- Шаблон новой клиники: `private.seed_organization()`.
- Правила сделок (отказ, перенос между воронками, метки времени, журнал): триггеры `handle_deal_before_write` / `handle_deal_after_write`. Правила воронок: отложенный триггер `check_pipeline_stages`.
- Сумма оплат: `handle_deal_payment_changed`. Поле `paid_amount` защищено от ручной записи.
- Поиск по телефону: `find_patients_by_phone()`.
- Новая воронка создаётся функцией `create_pipeline()`: воронка сразу получает этапы «успех» и «отказ».
- Интерфейс берёт воронки и справочники из базы (`dictionaries/useDictionaries.ts`). Настройки стадий и категорий в конфигурации Atomic CRM больше не используются.

## Исправления этапа 1, найденные e2e-тестами

В этой среде удалось поднять настоящий Supabase в Docker и впервые прогнать e2e. Нашлись три ошибки, исправлены в миграции `20260929000000_invites_and_clinic_deletion.sql`. В ней же включено правило переноса сделки в другую воронку: раньше настройка сохранялась, но не применялась.

1. **Приглашённый сотрудник получал собственную клинику.** Supabase Auth сначала создаёт пользователя, а клинику и роль (`app_metadata`) записывает вторым запросом. Триггер на создание пользователя их ещё не видел. Теперь сотрудник присоединяется к клинике в момент записи `app_metadata`. Новую клинику создаёт только форма регистрации (она передаёт `organization_name`). SQL-хелпер `tests.invite` теперь повторяет эти два шага Supabase Auth, поэтому тест ловит ошибку.
2. **Клинику нельзя было удалить.** Каскадное удаление убирало сотрудников и справочники раньше, чем ссылающиеся на них оплаты и задачи. Теперь сначала удаляются пациенты, а вместе с ними всё клиническое.
3. **Удаление заметки через API падало:** при схлопывании миграций Atomic CRM потерялось расширение `pg_net`.

## Известные ограничения

- В этой среде edge runtime не может скачать зависимости с jsr.io (прокси подменяет сертификат). Поэтому приглашение через форму «Сотрудники» проверено на уровне Auth API — тем же вызовом, что делает функция `users`. Сам интерфейс формы проверит CI.
- Мобильная вёрстка Atomic CRM убрана: CRM рассчитана на десктоп.
- Теги в интерфейсе сделки, общая лента в карточке (чат + задачи + заметки + история), фильтры по периоду и тегам, задачи по сотрудникам для руководителя — этап 3. Непрочитанные сообщения — этап 4.
