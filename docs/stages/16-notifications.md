# Этап 16. Уведомления сотрудникам и контроль скорости ответа

Заказчик: медленный первый ответ — главная причина, по которой клиника теряет лиды. Раньше сотрудники не получали никаких уведомлений.

## Что появилось

### Уведомления

Четыре вида уведомлений. Каждое получает конкретный сотрудник.

- **«Вам назначена сделка»** (`lead_assigned`). Сделка стала вашей:
  - по распределению (по очереди);
  - по «кто первый ответил»;
  - руководитель или коллега переназначил её на вас.

  За собственное действие уведомления нет. Нет его, если вы создали сделку на себя, забрали её себе или ответили первым.
- **«Новое сообщение»** (`patient_message`). Пациент написал в сделку, где вы ответственный. Сообщение по сделке без ответственного получают:
  - в режиме «кто первый ответил» — выбранные в распределении сотрудники (если список пуст — все);
  - в остальных режимах — владелец и руководители.

  Несколько сообщений по одной сделке подряд не засыпают колокольчик. Если прошлое уведомление ещё не прочитано и ему меньше 5 минут, обновляется оно: «Новые сообщения (3)», «Асель, 3 сообщения: …».

  Новый лид, который распределение сразу отдало сотруднику, даёт одно уведомление — о назначении, без второго о сообщении.
- **«Задача просрочена»** (`task_overdue`). Срок вашей задачи прошёл. Уведомление приходит один раз. Если срок перенесли, а задача снова просрочена, придёт ещё одно. Задачи, просроченные больше суток назад (например, до запуска этапа), не объявляются.
- **«Пациент ждёт ответа»** (`response_overdue`). См. «Контроль ответа» ниже.

### Где видны уведомления

- **Колокольчик в шапке**, рядом с переключателем темы:
  - число непрочитанных;
  - по клику — список, свежие сверху;
  - клик по уведомлению открывает сделку и отмечает уведомление прочитанным;
  - кнопка «Прочитать все».

  Колокольчик опрашивает базу каждые 20 секунд, как «Входящие». Realtime в проекте не настроен.
- **Уведомления браузера.** Кнопка «Включить уведомления в браузере» есть в колокольчике и в профиле. Браузер спросит разрешение. Новые уведомления всплывают, пока открыта вкладка CRM. Клик открывает сделку.
- **Telegram.** Профиль → «Подключить Telegram». CRM показывает ссылку `t.me/<бот>?start=<код>` и команду `/start <код>`. Код одноразовый и действует 30 минут. После «Старт» бот отвечает «Готово!», и уведомления приходят в этот чат.
  - `/stop` в боте или «Отключить» в профиле отвязывают чат.
  - Если сотрудник заблокировал бота, чат отвязывается сам.
- **Настройки сотрудника** (профиль → «Уведомления»):
  - какие виды уведомлений присылать;
  - куда: браузер, Telegram.

  В колокольчике видно всё всегда. Выбор видов действует на браузер и Telegram.

### Контроль ответа

**Настройки → «Контроль ответа»** (владелец и руководитель):
- включить или выключить контроль;
- лимит ответа — N минут (по умолчанию 15);
- рабочие часы — по умолчанию с 9:00 до 21:00 по часовому поясу клиники (`organizations.timezone`);
- кого предупредить:
  - ответственного (у сделки без ответственного — тех, кому приходят её сообщения);
  - владельца и руководителей;
  - дополнительно выбранных сотрудников.

**Правило.** Сделка «ждёт ответа», если выполнены три условия:
1. Она открыта (не успех, не отказ, не в архиве).
2. После последнего ответа клиники пришло входящее сообщение.
3. С первого такого сообщения прошло больше N **рабочих** минут. Минуты вне рабочих часов не считаются.

Ответ клиники — исходящее сообщение сотрудника или ответ с телефона. Автосообщение (этап 6) ответом не считается: пациент всё ещё ждёт человека.

- **Канбан:** на карточке сделки красная плашка «Ждёт ответа 23 мин».
- **Список сделок:** быстрый фильтр «Ждут ответа».
- **Рабочий стол:** виджет «Ждут ответа» — такие сделки, дольше всех ждущие сверху.
- **Оповещения:** уведомление «Пациент ждёт ответа» уходит настроенным людям один раз за эпизод ожидания. Эпизод заканчивается ответом клиники; следующее сообщение пациента начинает новый. Когда ожидание достигает 3×N, владелец и руководители получают ещё одно уведомление, «Пациент всё ещё ждёт ответа».

## Как подключить Telegram-бота уведомлений

Бот один на всю платформу. Это не бот клиники для пациентов, а бот, который пишет сотрудникам.

1. **Создать бота.** В Telegram откройте [@BotFather](https://t.me/BotFather), команда `/newbot`. Задайте имя (например, «DentalCRM уведомления») и username (например, `dentalcrm_notify_bot`). BotFather выдаст токен.
2. **Секреты edge-функций:**
   ```
   npx supabase secrets set NOTIFY_TELEGRAM_BOT_TOKEN=<токен от BotFather>
   npx supabase secrets set NOTIFY_TELEGRAM_WEBHOOK_SECRET=<случайная строка>
   npx supabase secrets set NOTIFICATIONS_DISPATCH_KEY=<ещё одна случайная строка>
   npx supabase secrets set NOTIFY_APP_URL=https://<адрес CRM>   # необязательно: ссылка «Открыть сделку»
   ```
3. **Задеплоить функции:**
   ```
   npx supabase functions deploy notify_telegram_webhook
   npx supabase functions deploy notifications_dispatch
   ```
4. **Зарегистрировать вебхук бота** (секрет — тот же, что `NOTIFY_TELEGRAM_WEBHOOK_SECRET`):
   ```
   curl "https://api.telegram.org/bot<токен>/setWebhook" \
     -d "url=https://<project-ref>.supabase.co/functions/v1/notify_telegram_webhook" \
     -d "secret_token=<NOTIFY_TELEGRAM_WEBHOOK_SECRET>" \
     -d 'allowed_updates=["message"]'
   ```
5. **Vault для pg_cron**, как на этапе 6. `project_url` уже есть, если настроены автосообщения:
   ```sql
   select vault.create_secret('<NOTIFICATIONS_DISPATCH_KEY>', 'notifications_dispatch_key');
   select vault.create_secret('https://<project-ref>.supabase.co', 'project_url');
   ```
6. **Username бота во фронтенде** (для кнопки «Открыть бота»): переменная сборки `VITE_NOTIFY_TELEGRAM_BOT=dentalcrm_notify_bot`. Без неё профиль показывает только команду `/start <код>`.

Без секретов в Vault задание cron по-прежнему отмечает просроченные задачи и ожидающих пациентов (колокольчик работает), но в Telegram ничего не уходит. Функцию `notifications_dispatch` можно вызвать и вручную с ключом service role.

## Как устроено

- **Схема** — отдельный файл `supabase/schemas/16_notifications.sql`, миграция `20261010000000_notifications.sql`. Существующие функции и триггеры не менялись, добавлены новые триггеры.
- **Таблицы:**
  - `notifications`: получатель, вид, заголовок, текст, ссылки на сделку, пациента и задачу, `message_count`, `read_at`, статус отправки в Telegram;
  - `notification_preferences`: виды, каналы, чат Telegram, одноразовый код;
  - `response_alerts`: какие оповещения об ожидании уже ушли — эпизод и уровень 1 или 2.
- **Колонки:**
  - в `organization_settings` — `response_*` (лимит, часы, кого оповещать);
  - в `tasks` — `overdue_notified_at`.
- **Триггеры:**
  - `deal_notify_assignment` (сделки) → `lead_assigned`. Автор изменения — `private.current_sales_id()`. Первый ответ распознаётся по исходящему сообщению того же сотрудника в этой же транзакции.
  - `message_notify` (входящие сообщения) → `patient_message` со склейкой.
  - `task_due_changed` сбрасывает отметку просрочки при переносе срока.
  - Массовая запись (импорт, перенос данных) может выключить уведомления для своей транзакции: `set local crm.notifications = 'off'`. Иначе импорт сделок с ответственными засыплет сотрудников уведомлениями «Вам назначена сделка».
- **Ожидание ответа:**
  - `private.deal_waiting_since()` — с какого сообщения пациент ждёт;
  - `private.working_minutes()` — рабочие минуты в часовом поясе клиники;
  - представление `deals_waiting` (security invoker) — открытые сделки, которые ждут: минуты, лимит, флаг `overdue`.

  Те же правила в приложении — `providers/commons/responseTime.ts` (демо и фильтр).
- **Периодическое задание:**
  - `pg_cron` раз в минуту вызывает `private.notifications_tick()`. Оно делает три вещи:
    1. отмечает просроченные задачи;
    2. рассылает оповещения об ожидании;
    3. если есть что отправить в Telegram, через `pg_net` зовёт `notifications_dispatch`.
  - Задание `notifications-tick` создаётся миграцией, только если `pg_cron` установлен.
  - Сделки, которые уже ждали ответа в момент миграции, оповещений не получают (миграция отмечает их в `response_alerts`).
- **Telegram:**
  - `public.claim_telegram_notifications()` (только service role) берёт новые уведомления привязанных сотрудников с `FOR UPDATE SKIP LOCKED` и помечает их `sending`. Выключенные сотрудником виды получают статус `skipped`. Строка, зависшая в `sending` дольше 10 минут, получает `failed`: лучше так, чем отправить дважды.
  - Текст сообщения собирает `supabase/functions/_shared/notify.ts`. Там же разбор команд бота и ответы на них.
  - Привязка чата — `public.link_telegram_chat()` (только service role), по коду из `public.create_telegram_link_code()`.
- **Права:**
  - сотрудник читает только свои уведомления и может менять в них только `read_at`;
  - создать, удалить или переписать уведомление нельзя;
  - настройки уведомлений и код Telegram — только через функции для текущего пользователя;
  - таблицы `notification_preferences` и `response_alerts` клиентам закрыты;
  - изоляция клиник — по `organization_id` и составным внешним ключам.
- **Демо (FakeRest):**
  - у демо-пользователя несколько уведомлений в колокольчике;
  - три сделки ждут ответа, две — дольше лимита;
  - рабочие часы демо — круглосуточно, чтобы это было видно в любое время;
  - «Подключить Telegram» показывает код, но бота в демо нет.

    - сотрудник создал сделку себе;
    - переназначение;
    - распределение по очереди;

  - **Telegram:** код, привязка сервисной ролью, повтор и просроченный код, выбор строк диспетчером, пропуск выключенных видов, отвязка;

## Известные ограничения

- **Не проверено вживую:** отправка в Telegram и вебхук бота. В песочнице нет ни бота, ни Supabase. Edge-функции не запускались, логика вынесена в базу и в `_shared/notify.ts` и покрыта тестами. e2e в песочнице тоже не запускался.
- **Push через service worker** (уведомления при закрытой вкладке) не сделан: нужен push-сервер и ключи VAPID. Уведомления браузера работают, пока открыта вкладка.
- **Колокольчик опрашивает базу** раз в 20 секунд. Уведомление может появиться с задержкой до 20 секунд, а в Telegram — до минуты (интервал cron).
- **Рабочие часы одинаковы для всех дней.** Выходных и праздников нет.
- **Время ожидания на карточке** обновляется раз в 30 секунд.
- **Отчёты:** доля первых ответов в пределах N минут по сотрудникам в KPI **не добавлена**. Для этого пришлось бы менять `report_speed` (этап 7), `reportMath.ts` и таблицу KPI. Пока есть среднее время первого ответа.
