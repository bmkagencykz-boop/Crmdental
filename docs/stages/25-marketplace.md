# Этап 25. Маркет интеграций, приложения разработчиков и доступ интегратора

## Что появилось

**Интеграции** (`/#/integrations`, пункт «Интеграции» в боковом меню и ссылка «Маркет интеграций» в настройках — для владельца, руководителя и интегратора). Каталог всего, что клиника подключает, как маркет amoCRM:
- фильтр-категории с числом интеграций: Все, Подключено, Мессенджеры, Телефония, МИС, Сайт и заявки, API и вебхуки, Импорт, Приложения разработчиков; поиск по названию, разработчику, описанию и синонимам («вотсап» находит Wazzup24);
- «Все» без поиска группирует карточки по категориям; подключённые идут первыми, «Скоро» — последними;
- карточка: плитка-монограмма (без декоративных иконок), название, категория и разработчик, одна строка описания и статус «Подключено», «Доступно», «Бета» или «Скоро»;
- клик открывает интеграцию: описание, «Что умеет», раздел «Подключение» с настройками (те же экраны, что в Настройках) и «Отключить», когда интеграция подключена. Ссылка `/#/integrations?open=wazzup` открывает интеграцию сразу, `?category=telephony` — категорию.

В каталоге:
- Мессенджеры: Wazzup24, Telegram-бот клиники;
- Телефония: Binotel, Zadarma, Mango Office, Sipuni, Другая АТС (экран телефонии этапа 12);
- МИС: Dentist Plus и MacDent (заглушка «Скоро» с кнопкой «Оставить заявку»), IDENT, Dentalpro, MedElement, 1С:Медицина (экран МИС этапа 11);
- Сайт и заявки: Сайт и Tilda, 2GIS (бета);
- API и вебхуки: ключи, вебхуки и документация этапа 20;
- Импорт: Excel и CSV, перенос из amoCRM (мастер импорта);
- Приложения разработчиков: приложения, зарегистрированные в клинике.

**Приложения разработчиков.** Интегратор, владелец или руководитель регистрирует приложение («Зарегистрировать приложение»): название, идентификатор (латиницей, одинаковый во всех клиниках), описание, разработчик и контакт, сайт, адрес настроек приложения (необязательно), доступы и вебхук с событиями.
- «Установить» создаёт API-ключ приложения ровно с выбранными доступами и, если есть доступ «Вебхуки», подписку на события. Ключ и секрет вебхука показываются один раз — их передают разработчику.
- «Отключить» отзывает ключ приложения и удаляет его вебхуки; повторная установка выдаёт новый ключ. Доступы и вебхук установленного приложения не меняются — сначала отключите.
- «Экспорт манифеста» — JSON приложения; «Установить по манифесту» в другой клинике: вставить JSON, «Проверить», посмотреть доступы, «Установить». Повторный импорт того же манифеста обновляет приложение (пока оно не установлено).
- Ключи приложений видны в Настройки → API и вебхуки с пометкой «Приложение».

Доступы (scopes): `deals:read`, `deals:write`, `patients:read`, `patients:write`, `messages:read`, `messages:write`, `tasks`, `settings:read`, `settings:write`, `pipelines:write`, `salesbot:write`, `webhooks`. Ключи «Чтение» и «Чтение и запись» этапа 20 работают как раньше: «Чтение» = `deals:read`, `patients:read`, `settings:read`; «Чтение и запись» — плюс `deals:write`, `patients:write`.

Манифест:

```json
{
  "manifest_version": 1,
  "id": "roistat-like-analytics",
  "name": "Сквозная аналитика Roistat-like",
  "description": "Источники заявок и выручка по каналам",
  "developer": { "name": "Digital Agency", "contact": "hello@agency.kz", "website": "https://agency.kz" },
  "settings_url": "https://agency.kz/analytics",
  "scopes": ["deals:read", "patients:read", "settings:read", "webhooks"],
  "webhook": { "url": "https://agency.kz/hooks/dentalcrm", "events": ["deal.created", "payment.added"] }
}
```

**Доступ интегратора.** Новая роль «Интегратор» — технический аккаунт агентства, которое настраивает клинику (как технический аккаунт amoCRM). Владелец приглашает его в Сотрудники → «Новый сотрудник», роль «Интегратор», с датой «Доступ до» (пусто — без срока) и переключателем «Доступ к переписке».
- Интегратор настраивает всё: воронки и этапы, цифровую воронку, автозадачи, чек-листы, автосообщения и шаблоны, быстрые ответы клиники, поля, услуги, источники, причины отказа, врачей, повторные продажи, распределение, мессенджеры, телефонию, заявки с сайта, API, вебхуки и приложения. Когда появится салесбот, его экраны используют то же правило (`configuration` / `edit`).
- Сделки и пациентов интегратор только просматривает (все сделки клиники, какой бы ни была видимость для администраторов), чтобы проверять автоматизации: не создаёт, не меняет, не удаляет, не пишет заметки и задачи, не отправляет сообщения, не разбирает «Неразобранное».
- Не видит оплаты, отчёты, план продаж, журнал действий, рассылки, сотрудников; не импортирует данные, не объединяет пациентов, не меняет профиль клиники.
- Тексты переписки скрыты, пока владелец не включит «Доступ к переписке».
- После даты «Доступ до» аккаунт ведёт себя как отключённый: вход закрыт с сообщением «Доступ закрыт…», данные клиники не видны.
- Меню интегратора: «Сделки», «Интеграции», «Настройки»; вверху страницы — плашка «Технический доступ интегратора до 21.10.2026». Интегратор не бывает ответственным за сделку.
- Все действия интегратора — в журнале действий с его именем; изменение срока доступа и доступа к переписке — там же.

## API для интеграторов

Все методы — на адресе API клиники (`https://<проект>.supabase.co/functions/v1/api`), с заголовком `Authorization: Bearer <ключ>`; лимит 60 запросов в минуту на ключ. Без нужного доступа метод отвечает `403 insufficient_scope` (ключ «Чтение» этапа 20 на запись — `403 read_only_key`).

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/account` | settings:read | Клиника: название, часовой пояс, валюта, сотрудники, воронки с этапами |
| GET | `/api/pipelines` | settings:read | Воронки с этапами (этап 20) |
| POST | `/api/pipelines` | pipelines:write | Новая воронка: `name`, `stages` `[{ name, kind, color }]`; без stages — «Новый лид», «Успешно», «Отказ» |
| PATCH | `/api/pipelines/:id` | pipelines:write | `name`, `position`, `is_default` |
| GET | `/api/stages?pipeline_id=` | settings:read | Этапы |
| POST | `/api/stages` | pipelines:write | `pipeline_id`, `name`, `kind` (open, won, lost), `color`, `position`, `script`; без position — перед «Успешно» и «Отказом» |
| PATCH | `/api/stages/:id` | pipelines:write | `name`, `kind`, `color`, `position`, `script` |
| GET | `/api/stage_triggers?pipeline_id=&stage_id=` | settings:read | Триггеры цифровой воронки |
| POST | `/api/stage_triggers` | pipelines:write | Триггер: колонки `stage_triggers` — `stage_id`, `event`, `action` и поля действия, условия |
| PATCH | `/api/stage_triggers/:id` | pipelines:write | Меняются только переданные поля |
| DELETE | `/api/stage_triggers/:id` | pipelines:write | Удаление триггера |
| GET | `/api/custom_fields?entity=deal` | settings:read | Дополнительные поля |
| POST | `/api/custom_fields` | settings:write | `entity`, `name`, `type`, `options`, `required`, `show_on_card` |
| GET | `/api/tasks?deal_id=&done=false` | tasks | Задачи, `page`, `per_page` |
| POST | `/api/tasks` | tasks | `deal_id`, `type`, `text`, `due_date`, `sales_id` (без него — ответственному сделки), `duration_minutes` |
| GET | `/api/messages?deal_id=` | messages:read | Переписка сделки |
| POST | `/api/messages` | messages:write | `{ deal_id, text }` — сообщение пациенту, ответ `202` |

Методы сделок и пациентов этапа 20 требуют `deals:read` / `deals:write` и `patients:read` / `patients:write`.

**Как отправляется сообщение.** `POST /api/messages` не вызывает `messenger_send` напрямую (для него нужен вход сотрудника), а ставит сообщение в очередь автосообщений этапа 6 без правила и шаблона, с готовым текстом: диспетчер `automessages_dispatch` отправляет его в течение минуты через канал переписки пациента (Wazzup24 или Telegram-бот), сообщение появляется в ленте сделки. Если мессенджеры не подключены — `422 rule_violation`. Если сделка уйдёт с этапа до отправки, сообщение отменяется, как любое автосообщение.

Примеры:

```bash
KEY="dcrm_…"
API="https://<проект>.supabase.co/functions/v1/api"

# Клиника: сотрудники и воронки
curl -H "Authorization: Bearer $KEY" "$API/account"

# Новая воронка со своими этапами
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/pipelines" \
  -d '{"name": "Ортодонтия", "stages": [{"name": "Заявка"}, {"name": "Консультация"}, {"name": "Лечение начато", "kind": "won"}, {"name": "Отказ", "kind": "lost"}]}'

# Переименовать воронку
curl -X PATCH -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/pipelines/4" \
  -d '{"name": "Ортодонтия (брекеты и элайнеры)"}'

# Этап перед «Успешно»
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/stages" \
  -d '{"pipeline_id": 4, "name": "План лечения", "color": "#F47C9C"}'

# Скрипт этапа
curl -X PATCH -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/stages/17" \
  -d '{"script": "Уточните удобное время первого визита"}'

# Цифровая воронка: ответил пациент — перевести «В работу»
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/stage_triggers" \
  -d '{"stage_id": 15, "event": "message_in", "action": "move_stage", "target_stage_id": 16, "name": "Ответил — в работу"}'

# Выключить и удалить триггер
curl -X PATCH -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/stage_triggers/9" -d '{"is_active": false}'
curl -X DELETE -H "Authorization: Bearer $KEY" "$API/stage_triggers/9"

# Поле сделки «Рекламная кампания»
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/custom_fields" \
  -d '{"entity": "deal", "name": "Рекламная кампания", "type": "select", "options": ["Instagram", "2GIS", "Сайт"]}'

# Задача по сделке и открытые задачи
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/tasks" \
  -d '{"deal_id": 123, "type": "call", "text": "Перезвонить после консультации", "due_date": "2026-10-15T11:00:00+05:00"}'
curl -H "Authorization: Bearer $KEY" "$API/tasks?deal_id=123&done=false"

# Переписка сделки и сообщение пациенту
curl -H "Authorization: Bearer $KEY" "$API/messages?deal_id=123"
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" "$API/messages" \
  -d '{"deal_id": 123, "text": "Асель, напоминаем о визите завтра в 10:30"}'
```

Та же документация — на странице «Документация API» (Настройки → API и вебхуки → «Документация API»), с адресом API клиники в примерах.

## Как подключить

1. Применить миграцию `20261021000000_marketplace.sql` и задеплоить edge-функции `api`, `users`, `messenger_send`, `messenger_connect`, `telegram_connect` (изменились проверки ролей и маршруты API).
2. Новых секретов нет: сообщения API уходят тем же диспетчером автосообщений (pg_cron этапа 6).

## Как устроено

- `supabase/schemas/25_marketplace.sql`: таблица `developer_apps` (определение приложения и его установка), колонки `api_keys.scopes`, `api_keys.app_id`, `webhooks.app_id`, `sales.access_expires_at`, `sales.can_read_messages`; функции `install_developer_app`, `uninstall_developer_app`, `import_app_manifest`, `set_integrator_access` (только владелец), `private.api_authorize` (ключ + доступ), `private.can_configure`, `private.can_read_messages` и все новые `api_*`.
- Права интегратора собраны в одном месте, в том же файле: разрешающие политики «Integrator can …» рядом с политиками владельца и руководителя для таблиц настроек (воронки, этапы, услуги, источники, причины, автозадачи, чек-листы, шаблоны и правила автосообщений, врачи, быстрые ответы клиники, повторные продажи, поля, триггеры, вебхуки, ключи) и ограничивающие (`as restrictive`) «Integrators cannot …» на сделках, пациентах, заметках, задачах, звонках, чек-листах сделок, файлах, очереди автосообщений; «Integrators do not see payments» на оплатах и «Integrators see messages with access» на сообщениях. Представления `security_invoker`, поэтому `deals_summary.last_message_text` тоже скрыт.
- Функции прежних этапов, где проверялось `in ('owner', 'head')` для настроек, пропускают интегратора: мессенджеры и Telegram-бот (статус), заявки с сайта, телефония, заявка на МИС, вебхуки и ключи API; `private.manager_deal_visibility()` даёт интегратору все сделки; `merge_unsorted` интегратору запрещена; отчёты, рассылки, импорт, объединение пациентов, профиль клиники — нет.
- Срок доступа: `private.current_organization_id()`, `current_user_role()`, `current_sales_id()` не находят сотрудника после `access_expires_at` — RLS и функции видят его как отключённого; edge-функции получают `disabled: true` из `getUserSale`; вход в приложение закрывается с сообщением.
- `invited_role()` и функция `users` принимают роль `integrator`; срок и доступ к переписке сохраняет `set_integrator_access` после приглашения.
- Доступы API: каждая `api_*` вызывает `private.api_authorize(ключ, доступ)`; ключ без `scopes` получает права этапа 20 (`private.api_key_scopes`). Ошибка `PT403` с подсказкой `insufficient_scope` превращается в `403 insufficient_scope`.
- `claim_automessages` отправляет строку очереди без правила и шаблона с готовым текстом (сообщения API).
- Интерфейс: `src/components/atomic-crm/integrations/` — `catalog.ts` (реестр: одна запись + компонент настроек), `catalogModel.ts` (фильтры, поиск, статусы), `manifest.ts` (манифест, доступы методов), `IntegrationsPage.tsx`, `DeveloperApps.tsx`, `MisComingSettings.tsx`, `IntegratorBanner.tsx`. Права в интерфейсе — `canAccess` (`integrations`, `import`, `organization`, действие `menu` для бокового меню).
- Точки расширения: салесбот (этап 26) добавляет запись в `CATALOG` или раздел настроек, проверяет `configuration` / `edit` и доступ `salesbot:write` в своих `api_*` через `private.api_authorize`; коннекторы МИС и Sipuni (этап 27) заменяют настройки записей `dentist_plus`, `macdent` (сейчас `MisComingSettings`, статус «coming») и `sipuni` (сейчас экран телефонии).
- Демо (FakeRest): Wazzup24 подключён, Sipuni доступен, Dentist Plus «Скоро», установлено приложение «Сквозная аналитика Roistat-like» от Digital Agency (ключ и вебхук), есть интегратор `integrator@digital-agency.kz` (доступ на 30 дней, без переписки). Те же правила интегратора: сделки только чтение, без оплат и переписки.

## Известные ограничения

- Интеграция отключается кнопкой «Отключить» только там, где у экрана есть отключение (Wazzup24, Telegram-бот, телефония, приложения); МИС, заявки с сайта и API отключаются в своих экранах (отзыв ключа, новый токен).
- Статус «Подключено» у «Сайт и Tilda» — если через вебхук пришла хотя бы одна заявка; 2GIS своего признака подключения не имеет.
- Канбан не запрещает интегратору перетаскивать карточки: база отклоняет изменение, и появляется сообщение об ошибке.
- Уже открытая сессия интегратора после истечения срока не выкидывается сразу: данные перестают загружаться, вход заново закрыт.
- Сообщение `POST /api/messages` уходит через очередь, в течение минуты, а не мгновенно; файлы через API не отправляются.
- Для отдельных клиник доступ приложения нельзя сузить после установки — только переустановить с другими доступами.
