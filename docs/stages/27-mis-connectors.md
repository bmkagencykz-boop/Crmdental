# Этап 27. Коннекторы МИС (Dentist Plus, MacDent) и телефония Sipuni

## Что появилось

**Интеграция с МИС** (Настройки → «Интеграция с МИС», владелец и руководитель). Dentist Plus и MacDent теперь подключаются по-настоящему. IDENT, Dentalpro, MedElement и 1С:Медицина остались «скоро» с кнопкой «Оставить заявку».

Настройки каждой МИС — одинаковые:
- **Подключение.** Адрес API (можно оставить пустым: подставится адрес по умолчанию) и ключ API. Ключ хранится только на сервере и больше не показывается. Кнопки «Подключить» / «Сохранить», «Проверить подключение», «Синхронизировать сейчас», «Отключить». Результат проверки и синхронизации виден сразу под кнопками.
  - Dentist Plus: ключ создаётся в «Настройки → Интеграции».
  - MacDent: ключ и документацию выдаёт поддержка MacDent директору клиники или доверенному лицу.
- **Что синхронизировать** — переключатели:
  - пациенты из МИС;
  - записи и визиты из МИС;
  - оплаты из МИС;
  - передавать записи из CRM в МИС (по умолчанию выключено).
- **Статусы МИС и этапы сделки.** Для каждого статуса записи выбирается этап или тег:
  - «Записан» и «Запись подтверждена» → «Записан»;
  - «Пришёл» и «Визит состоялся» → «Пришёл на консультацию»;
  - «Лечение начато» → «В лечении»;
  - «Отменён» и «Не пришёл» по умолчанию ничего не делают: можно выбрать этап или тег (например, «Отменил визит»).

  Так настроено сразу после подключения, если этапы клиники называются как в шаблоне. Этап отказа выбрать нельзя: отказу нужна причина.
- **Врачи МИС.** Врачи сопоставляются с врачами клиники по ФИО (точное совпадение, иначе единственный врач с такой фамилией). Кого не узнали — выбирается вручную, визиты этого врача подтягиваются.
- **Адрес для МИС** с кнопками «Скопировать» и «Новый адрес» — если МИС умеет отправлять события на внешний адрес. Иначе CRM сама забирает изменения каждые 10 минут.
- **Журнал синхронизации** — 50 последних событий: время, что пришло (пациент, запись, визит, оплата, этап сделки, синхронизация, проверка, передача записи), результат («Успешно», «Пропущено», «Ошибка»), подробности и ссылка на сделку.
- **Что нужно уточнить по документации вендора** — блок со списком того, что коннектор пока предполагает (см. «Известные ограничения»).

**Что делает синхронизация:**
- **Пациент:** ищется по ID в МИС, затем по телефону в любом написании. Если не найден — создаётся с источником «МИС». У найденного дописываются только пустые поля и новые телефоны. Имя из номера телефона (пациент со звонка) заменяется настоящим.
- **Запись на приём:**
  - попадает в последнюю открытую сделку пациента; если открытой нет — создаётся новая сделка с источником «МИС», сразу на этапе своего статуса;
  - заполняются «Запись на приём», врач и услуга (услуга — если такая есть в справочнике);
  - сделка двигается по сопоставлению статусов: только вперёд и только внутри своей воронки. Закрытая сделка не двигается. Чек-лист этапа может остановить перевод, как и для цифровой воронки. Пропущенный перевод виден в ленте сделки («Автоматизация пропущена — … (правило «МИС: Dentist Plus»)») и в журнале;
  - отменённая запись освобождает дату записи сделки; для пациента без открытой сделки новая сделка не создаётся.
- **Визит состоялся** заполняет «Визит» и переводит сделку по статусу «Визит состоялся» или «Лечение начато».
- **Оплата** добавляется в оплаты сделки (оплата или предоплата) ровно один раз — по ID оплаты в МИС.
- Все изменения в журнале действий — с источником «МИС». Смена этапа запускает автозадачи, автосообщения и триггеры цифровой воронки, как обычный переход.

**Передача записей в МИС** (если включена): когда сделка переходит на этап статуса «Записан» с заполненной датой записи, пациент (если МИС его ещё не знает) и запись отправляются в МИС. Изменения, пришедшие из МИС, обратно не отправляются: ни сами записи, ни даты, которые МИС уже знает.

**Карточка сделки и пациента:**
- на сделке, синхронизированной с МИС, — небольшая отметка «МИС» рядом с тегами;
- блок «Визиты из МИС» — под пациентом в сделке и в карточке пациента: дата, статус словами МИС, услуга и врач.

**Телефония Sipuni** (Настройки → Телефония → «Sipuni»):
- события АТС Sipuni создают звонки как у других АТС;
- начало, ответ и окончание обновляют один звонок по `call_id`;
- пропущенный входящий ставит задачу «Перезвонить»;
- ссылка на запись разговора сохраняется, если пришла;
- внутренний номер сотрудника (`short_dst_num` / `short_src_num`) определяет сотрудника.

CRM отвечает Sipuni `{"success": true}` — иначе Sipuni перестаёт присылать события. Секрет и API-ключ для Sipuni не нужны.

## Как подключить

### Dentist Plus / MacDent

1. Задеплоить функции: `npx supabase functions deploy mis_webhook mis_sync mis_test_connection` (все с `verify_jwt = false`, прописаны в `supabase/config.toml`; `mis_sync` и `mis_test_connection` сами проверяют сессию сотрудника или ключ диспетчера).
2. Секреты — те же, что у диспетчеров автосообщений и вебхуков: функция — `AUTOMESSAGES_DISPATCH_KEY`, Vault — `project_url` и `automessages_dispatch_key`. Миграция создаёт задания `pg_cron`:
   - `mis-sync` — каждые 10 минут забирает изменения всех подключённых МИС;
   - `mis-push` — каждую минуту отправляет очередь записей, если в ней что-то есть.
3. В CRM: Настройки → Интеграция с МИС → Dentist Plus (или MacDent) → ключ → «Подключить» → «Проверить подключение».
4. Если МИС умеет слать события — вставить в неё «Адрес для МИС».

### Sipuni

1. Настройки → Телефония → «Sipuni» → «Подключить».
2. Личный кабинет Sipuni → Настройки → API → «События на АТС»: вставить адрес CRM (`…/telephony_webhook?provider=sipuni&token=<токен>`), включить события начала, ответа и окончания звонка.
3. Указать внутренние номера сотрудников (как в Sipuni).

Как читаем данные Sipuni:
- `event`: 1 — начало, 3 — ответ, 2 — окончание, 4 — окончание вторичного плеча (пропускаем);
- `call_id` — один на все события звонка;
- `src_num` / `dst_num` и `src_type` / `dst_type` (1 — внешний номер, 2 — внутренний): внешний → внутренний — входящий, внутренний → внешний — исходящий, внутренний → внутренний — пропускаем. Без типов внутренним считается номер до 5 цифр;
- `status` окончания: `ANSWER` — принят, `BUSY`, `NOANSWER`, `CANCEL`, `CONGESTION`, `CHANUNAVAIL` — пропущен;
- длительность = `timestamp` окончания − `call_answer_timestamp`;
- время звонка — `call_start_timestamp` (Unix, UTC);
- `call_record_link` — ссылка на запись;
- `short_src_num` / `short_dst_num` — внутренние номера.

GET-запрос (событие в параметрах адреса), форма или JSON — принимается всё.

## Как устроено

- **Миграция** `20261023000000_mis_connectors.sql`, схема `supabase/schemas/27_mis_connectors.sql`; изменены `11_import_mis.sql` (виды МИС `dentist_plus`, `macdent`; сущности `external_refs`: `appointment`, `payment`, `doctor`) и `12_telephony.sql` (провайдер `sipuni` в таблице, `ingest_call` и `save_telephony`).
- **`integrations`** получила колонки подключения:
  - `base_url`, `api_key` (читает только service role), `webhook_token`;
  - направления `sync_patients`, `sync_appointments`, `sync_payments`, `push_appointments`;
  - `status_map` (`{ "<статус>": { "stage_id": … } | { "tag_id": … } }`), `sync_cursor`, `connected_at`.

  Таблица по-прежнему закрыта для сотрудников. Настройки — через функции (владелец и руководитель):
  - `mis_connection_status(kind)` — без ключа;
  - `save_mis_connection(kind, settings)` — `api_key`: `null` — оставить, пустая строка — удалить; проверяет адрес `https://` и сопоставление: этап клиники не из отказа или тег клиники;
  - `disconnect_mis`, `regenerate_mis_token`, `link_mis_doctor(mis_doctor_id, doctor_id)`.

  Статус для всех сотрудников — прежняя `integration_status()`, на ней же хук `useMisConnection(kind)` → `{ connected, status }`.
- **Новые таблицы:**
  - `mis_doctors` — врачи МИС и связь с врачами клиники (дублируется в `external_refs`, сущность `doctor`);
  - `mis_appointments` — визиты из МИС (видны как сделка; без сделки — всей клинике);
  - `mis_sync_log` — журнал, 90 дней, читают владелец и руководитель;
  - `mis_outbox` — очередь передачи записей в МИС.
- **Синхронизация — SQL-функции** (только service role) с нейтральным JSON:
  - `mis_upsert_patient`, `mis_upsert_appointment`, `mis_visit_completed`, `mis_upsert_payment`;
  - `mis_record_sync(connection, operation, ok, message, cursor)` — статус подключения, время и курсор синхронизации, строка журнала;
  - `claim_mis_outbox` / `complete_mis_outbox` — очередь по образцу вебхуков этапа 20 (`FOR UPDATE SKIP LOCKED`, повторы через 1, 5, 30 минут и 2 часа, после 5 попыток — `failed`).

  Каждая функция пишет журнал. Ошибка одной записи возвращается в ответе (`result: "error"`), а не прерывает пачку.
- **Правила перевода** — `private.mis_apply_status`:
  - только вперёд, в воронке сделки, не из закрытой сделки;
  - ошибка перевода (чек-лист, отказ) перехватывается и записывается как пропуск;
  - строка в `stage_trigger_runs` без триггера с именем «МИС: …» — её показывает лента сделки.
- **Защита от петли:**
  - функции синхронизации ставят `crm.audit_source = 'mis'` и `crm.mis_sync = 'on'`;
  - триггер `deal_mis_push` ставит запись в очередь, только если изменение сделано не под этими флагами и дата записи не совпадает с визитом, который уже пришёл из МИС;
  - после успешной передачи ID пациента и записи в МИС сохраняются, поэтому эхо из МИС узнаётся.
- **Edge-функции:**
  - `mis_webhook?kind=&token=` — события МИС (GET, форма или JSON);
  - `mis_sync` — `pg_cron` (`{mode: "poll" | "push"}`) или кнопка «Синхронизировать сейчас» (`{kind}`, сессия владельца или руководителя);
  - `mis_test_connection` — кнопка «Проверить подключение».
- **Адаптеры вендоров** — `supabase/functions/_shared/mis/`:
  - `normalize.ts` — терпимое чтение полей: русские и английские имена, snake/camelCase, вложенные объекты, даты `2026-10-15 10:30`, `15.10.2026`, Unix; статусы словами и кодами;
  - `adapter.ts` — сборка адаптера из конфига вендора: разбор записей, вебхуков, запросы;
  - `dentistPlus.ts`, `macdent.ts` — **по одному объекту-конфигу на вендора** со всеми предположениями и пометкой «уточнить по документации вендора»;
  - `sync.ts` — применение записей, опрос изменений с курсором, проверка ключа, передача записи.
- **Sipuni** — `sipuniToCall` в `_shared/telephony.ts`, `telephony_webhook` принимает GET для Sipuni и отвечает `{"success": true}` (даже на звонок, который CRM не приняла).
- **Интерфейс:**
  - `mis/DentistPlusSettings.tsx`, `mis/MacDentSettings.tsx` — самостоятельные компоненты для каталога интеграций; общий `mis/MisConnectorSettings.tsx`, доступ — `canAccess configuration edit`;
  - `mis/useMisConnection.ts`, `mis/MisVisits.tsx` (визиты и отметка «МИС»);
  - логика без React — `mis/misConnectors.ts`;
  - Sipuni — в `telephony/TelephonySettings.tsx`, тексты в пространстве `sipuni`.
- **Демо (FakeRest):**
  - Dentist Plus подключена;
  - у четырёх открытых сделок есть визиты из МИС (записан, подтверждён, состоялся, лечение начато), с врачами;
  - одна оплата из МИС;
  - в ленте — перевод и пропущенный из-за чек-листа перевод;
  - журнал синхронизации, врач МИС без сопоставления;
  - проверка, синхронизация, сопоставление и отключение работают (`providers/fakerest/misConnectors.ts`);
  - Sipuni доступна в телефонии.

## Известные ограничения — уточнить по документации вендора и проверить на живом аккаунте

- **API Dentist Plus и MacDent не проверены:** документация недоступна, песочница не пускает на сайты вендоров. Всё, что предполагается, лежит в `DENTIST_PLUS_CONFIG` и `MACDENT_CONFIG`:
  - адрес API: `https://api.dentist-plus.com/v1`, `https://app.macdent.kz/api/v1`;
  - ключ: заголовок `Authorization: Bearer` у Dentist Plus, параметр `access_token` у MacDent;
  - пути `/patients`, `/visits` или `/appointments`, `/payments`;
  - фильтр изменений `updated_from` / `updated_after`, страницы `page` + `per_page` / `limit`;
  - коды статусов, имена полей, формат вебхуков, создание пациента и записи через API.
- **Вебхуки МИС:** неизвестно, умеют ли вендоры слать события. Без них работает опрос каждые 10 минут.
- **Опрос без фильтра изменений** (если API его не поддерживает) будет каждый раз читать до 20 страниц. Функции идемпотентны, но это лишняя нагрузка — поправить `query.since` в конфиге.
- **Врачи** сопоставляются по ФИО; тёзки и разные написания — вручную.
- **Sipuni:** публичные библиотеки на GitHub (`sipuni/sipuni-api-php`, `sipuni/node-sipuni`) описывают только коллтрекинг, настройки и уведомления веб-телефона, но не «События АТС» и не выгрузку записей. Поэтому:
  - поля событий взяты из справки Sipuni и не проверены;
  - записи через REST API не запрашиваются — используется `call_record_link` из события.

  Проверить на живом аккаунте:
  - метод (GET/POST) и формат;
  - одинаков ли `call_id` во всех событиях;
  - значения `src_type` / `dst_type`;
  - приходит ли `call_record_link` и живёт ли ссылка долго;
  - что такое событие 4 в вашей схеме.
- **Edge-функции в песочнице не запускались** (нет Deno и Supabase). Логика — в SQL и в `_shared`, всё покрыто тестами.
