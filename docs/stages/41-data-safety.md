# Этап 41. Сохранность данных

## Что появилось

Перед работой настоящих клиник CRM защищает деньги и медицинские записи от случайного удаления, закрытую кассу — от правок задним числом, а ИИН и медицинские данные — от внешнего интегратора.

**Архив пациентов.**
- В карточке пациента (колонка справа) вместо «Удалить» — кнопка «В архив». После подтверждения пациент пропадает из списка пациентов, глобального поиска и выбора пациента в формах. Карта, сделки, оплаты, визиты и медицинские записи сохраняются, карточка открывается по ссылке.
- В шапке карточки и в строке списка — серая плашка «В архиве», в колонке справа — «В архиве с 12.05.2026».
- Список пациентов: кнопка-пилюля «Архив» показывает только архивных. Массовые действия списка — «В архив» (или «Вернуть из архива» в режиме «Архив») вместо удаления.
- «Вернуть из архива» — владелец и руководитель.
- «Удалить насовсем» (мелкая ссылка) — только владелец и только для пациента без оплат, визитов и медицинских записей, например созданного по ошибке. Для остальных — понятная ошибка «У пациента есть оплаты, визиты или медицинские записи — удалить его нельзя. Переместите пациента в архив».

**Сделки с оплатами** не удаляются ни из карточки, ни массовым действием: «По сделке есть оплаты — удалить её нельзя. Переместите сделку в архив».

**Закрытая смена кассы.** Операцию закрытой смены нельзя изменить (комментарий, время, способ оплаты) или отменить — ни в кассе, ни через оплату сделки: «Смена закрыта: операцию нельзя изменить или отменить. Проведите корректировку». Владелец исправляет сумму корректировкой, как раньше.

**Медицинские данные и интегратор.** ИИН, аллергии, противопоказания и хронические заболевания интегратор (внешнее агентство) больше не видит нигде: ни в карточке, ни в списке, ни в API базы; поиск по ИИН ему ничего не находит. Сотрудники работают как раньше: форма пациента, «Медицинская справка», шапка карточки, согласия.

**ИИН** уникален в клинике: второго пациента с тем же ИИН сохранить нельзя («Пациент с ИИН … уже есть в клинике»). Глобальный поиск находит пациента по ИИН (12 цифр, можно с пробелами). Страница «Дубли» предлагает объединить пациентов с одинаковым ИИН (причина «тот же ИИН»).

**Номер карты** новому пациенту присваивается автоматически — следующий номер клиники (1, 2, 3…; занятые номера пропускаются). Свой номер можно вписать в форме. Существующие пациенты без номера получили тот номер, который карточка уже показывала (номер пациента в CRM).

**Права по умолчанию.** Право «Пациенты → Удаление» (этап 30) теперь означает перемещение в архив. У администратора (менеджера) оно по умолчанию выключено, владелец может включить его в «Правах доступа». Руководитель и владелец архивируют как раньше удаляли.

**Вложения заметок, аватары и логотипы** лежат в закрытом хранилище: открыть файл по прямой ссылке без входа в CRM нельзя. Приложение показывает их по временным подписанным ссылкам (12 часов). Старые заметки со ссылками открываются как прежде.

**Очистка технических данных.** Каждую ночь (2:40 UTC) удаляются старые технические записи:

| Что | Срок хранения |
|---|---|
| Доставки вебхуков (доставлено / ошибка / отменено) | 90 дней |
| Журнал синхронизации МИС | 90 дней |
| Очередь отправки в МИС (выполнено / ошибка / отменено) | 90 дней |
| Прочитанные уведомления | 90 дней после прочтения |
| Журнал салесбота | 180 дней |
| Запуски триггеров digital pipeline (сделка уже не на этапе триггера) | 180 дней |
| Заявки с сайта (сырые данные формы) | 365 дней |
| Ответы HTTP-запросов pg_net | 7 дней |

Журнал изменений, деньги, медицинские данные и переписка не удаляются никогда.

### Права

| | Владелец | Руководитель | Администратор | Интегратор |
|---|---|---|---|---|
| В архив | ✓ | ✓ | если владелец дал право «Удаление» | — |
| Вернуть из архива | ✓ | ✓ | — | — |
| Удалить насовсем (пациент без истории) | ✓ | — | — | — |
| Удалить сделку с оплатами | — | — | — | — |
| Изменить / отменить операцию закрытой смены | — (корректировка) | — | — | — |
| ИИН, аллергии, противопоказания, хронические заболевания | ✓ | ✓ | ✓ (видимые пациенты) | — |

## Как устроено

- Схема `supabase/schemas/41_data_safety.sql`, миграция `20261112000000_data_safety.sql`. Изменены (и скопированы в миграцию):
  - внешние ключи `ON DELETE RESTRICT` — в своих файлах: `account_operations.patient_id` и `.deal_id` (36), `deal_payments.deal_id` (01), `visits.patient_id` (28), `treatment_plans.patient_id` (29), `patient_teeth`, `patient_tooth_history`, `visit_records`, `patient_questionnaires`, `patient_files`, `patient_consents` (37), `lab_orders.patient_id` (40). Остальные строки пациента (заметки, звонки, переписка, чаты, уведомления, отзывы, рассылки, заявки, файлы сделок, лист ожидания, записи МИС, сделки без оплат) по-прежнему удаляются вместе с ним — это переписка и автоматика, а не деньги и медицина;
  - `private.delete_organization_data` (02) — при удалении клиники сначала удаляет защищённые строки (операции, оплаты, наряды, медкарту, планы, визиты), затем пациентов;
  - `private.audit_row` (15) — строки `patient_medical` пишутся в журнал как изменения пациента;
  - `private.merge_patient_rows`, `private.patient_match_keys` (теперь plpgsql, причина `iin`), `public.merge_unsorted` (18) — медданные объединяются, «уступившие» зубы и анкета удаляются явно (раньше их убирал каскад), операции без оплаты сделки переносятся;
  - `private.access_default` (30) — «Пациенты → Удаление» администратора по умолчанию `none`;
  - `public.global_search` (31) — без архивных пациентов, поиск по ИИН;
  - `private.handle_patient_tooth_after_write` (37) — «уступивший» зуб при объединении не пишет историю;
  - `patients_summary` переопределено в 41: медданные — из `patient_medical`, в конце — `archived_at`, `archived_by`.
- **Архив**: `patients.archived_at`, `archived_by`; триггер `patient_archive` (`private.handle_patient_archive`) проверяет право (`access_scope('patients','delete')`, «Только свои» — свой пациент или пациент своей сделки), ставит время и автора сам (hint `patient_archive_forbidden` / `patient_restore_forbidden`). Скрытие — в приложении: `applyArchivedFilter` (`data-safety/dataSafety.ts`) добавляет `archived_at@is: null` ко всем спискам пациентов (список, выбор пациента), фильтр `archived: true` — архив.
- **Удаление**: триггер `patient_before_delete` — только владелец (hint `patient_delete_owner_only`; объединение пациентов ставит `crm.patient_merge`), только без истории (`private.patient_has_history`, hint `patient_has_history`, код 23503); каскад удаления клиники (`pg_trigger_depth() > 1`) проходит. `deal_before_delete` — сделка с `deal_payments` или `account_operations` (hint `deal_has_payments`).
- **Закрытая смена**: триггер `account_operation_shift_lock` (BEFORE UPDATE/DELETE). Разрешено: перепривязка (`patient_id`, `deal_id`, `plan_id`, `visit_id`, `branch_id` — объединения и SET NULL), каскад (`pg_trigger_depth() > 1`), кроме правки или удаления оплаты сделки напрямую (`crm.ledger_sync = 'deal'`). Hint `shift_closed`.
- **Медданные**: таблица `public.patient_medical` (`patient_id` — ключ, `iin`, `iin_duplicate`, `allergies`, `contraindications`, `chronic_diseases`, кто и когда). RLS: владелец, руководитель, администратор — для видимых пациентов; интегратор — ничего; запись только через `patients`.
  - Решение: колонки `patients.iin/allergies/contraindications/chronic_diseases` остались как путь записи — форма, «Медицинская справка», импорт, тесты пишут их как раньше. Триггеры `patient_medical_insert` (INSERT) и `patient_medical_<колонка>` (`UPDATE OF <колонка>` — колонка в SET, даже очищенная) переносят значение в `patient_medical` (`private.save_patient_medical`) и хранят в `patients` null. Внешний ключ `patient_medical → patients` отложенный (`DEFERRABLE INITIALLY DEFERRED`): строку пишет BEFORE INSERT пациента. Так любой читатель `patients` (включая интегратора и REST API) видит null, а приложение читает `patients_summary`.
  - Проверка ИИН (`patient_iin`, этап 37) срабатывает раньше и по-прежнему заполняет дату рождения и пол.
  - Уникальность: `patient_medical_iin_key` — уникальный индекс `(organization_id, iin) where iin is not null and not iin_duplicate`. Миграция отметила `iin_duplicate` у всех, кроме самого старого пациента с тем же ИИН; повторное сохранение того же ИИН флаг не снимает, новый ИИН — снимает и проверяется. Объединение оставляет ИИН сохраняемого пациента.
- **Номера карт**: `patient_card_counters` (счётчик клиники), `private.next_card_number` пропускает занятые, триггер `assign_patient_card_number`. Миграция: `card_number = id` у пациентов без номера, счётчик — максимальный числовой номер клиники.
- **Индексы**: `messages_patient_id_idx (organization_id, patient_id, sent_at desc)` — вкладка «История»; `account_operations_visit_id_idx`, `lab_orders_deal_id_idx` — внешние ключи с SET NULL/RESTRICT. Наряды по статусу и сроку, лист ожидания по статусу, операции по смене уже были проиндексированы.
- **Очистка**: `private.retention_tick()` (сроки — константы в функции, таблица выше), pg_cron `retention-daily` — `40 2 * * *`, создаётся миграцией, где pg_cron установлен. Не больше 50 000 строк на таблицу за запуск; возвращает число удалённых строк по таблицам.
- **Хранилище**: бакет `attachments` закрыт (`public = false`, в схеме 41 и в миграции); политики по папке клиники `<organization_id>/…` — прежние (07). В приложении — `providers/supabase/attachmentUrls.ts`: после чтения заметок, сотрудников и пациентов (и ленты активности) все файлы бакета получают подписанные ссылки одним запросом (`createSignedUrls`); путь берётся из `path` или из старого публичного URL (`attachmentPath`). При сохранении хранится постоянный адрес (`path` + URL вида `/object/public/…`), подписанная ссылка в базу не попадает. Логотипы в настройках и аватар в профиле — тоже по подписанным ссылкам. `public.note_attachment_paths_in_use` и функция `delete_note_attachments` не менялись.
- **Приложение**: `data-safety/PatientArchive.tsx` — `PatientArchiveActions` (карточка), `ArchivedBadge`, `ArchivedFilterToggle`, `BulkArchiveButton`; `canAccess` — действия `archive` (право «Удаление» пациентов), `restore` (владелец, руководитель), `delete` пациентов — только владелец.
- **Демо** (FakeRest): `providers/fakerest/dataSafety.ts` — архив и права, удаление пациентов и сделок, уникальный ИИН, номера карт, медданные скрыты от интегратора; закрытая смена — в `payments.ts`; объединение пациентов (`unsorted.ts`) переносит строки этапов 28–40; поиск — архив и ИИН (`search/globalSearch.ts`). Данные — `dataGenerator/dataSafety.ts`: номера карт у всех, два пациента без истории в архиве.

## Известные ограничения

- Архивный пациент по-прежнему находится по телефону при новом сообщении, звонке или заявке: обращение прикрепляется к нему, но из архива он автоматически не возвращается.
- Сделки архивного пациента остаются на доске, если их не закрыть или не архивировать отдельно.
- Колонки `patients.iin`, `allergies`, `contraindications`, `chronic_diseases` существуют, но всегда пусты — это путь записи; читать медданные нужно из `patients_summary` или `patient_medical`.
- Подписанная ссылка на вложение живёт 12 часов: на странице, открытой дольше, картинка обновится после перезагрузки данных.
- Интегратор видит заметки пациентов (как и раньше) и их вложения своей клиники.
- Номер карты не уникален: свой номер можно вписать совпадающим с чужим; автоматический номер занятые пропускает.
